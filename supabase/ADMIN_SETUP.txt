Адміністративна частина BankHotel

Налаштування
1. Supabase → SQL Editor → New query: встав весь 003_admin_rooms.sql і натисни Run.
   Скрипти 001 і 002 повторювати не потрібно.
2. Supabase → Authentication → Users: відкрий свій акаунт і скопіюй User UID.
3. У 004_grant_admin.sql заміни REPLACE_WITH_YOUR_USER_UUID на скопійований UID,
   залишивши одинарні лапки. Виконай цей запит у SQL Editor.
4. Відкрий локальний сайт через Live Server, онови Ctrl+F5 і увійди.
5. У хедері головної натисни Account, далі Manage rooms.
   Також можна відкрити /admin.html на тому самому локальному сервері.
   Якщо ти не увійшла, сторінка запропонує вхід і поверне до admin.html після нього.

Керування
- Add room: назва, унікальна адреса (наприклад garden-suite), опис,
  ціна за ніч, одна з наявних фотографій, її опис і доступність.
- Edit: редагування номера; адреса та ID залишаються незмінними для наявних посилань.
- Delete: видалення після підтвердження. Номер із будь-якими бронюваннями
  видалити не можна; вимкни Available for booking.
- Refresh: повторне отримання записів після змін або помилки мережі.
- Форма не повідомляє про успіх, доки Supabase не підтвердить операцію.

Де використовуються зміни
Сторінка бронювання завантажує номери, назви, ціни, фото й описи з Supabase.
Новий доступний номер з'явиться в її списку після оновлення сторінки.
Існуючі бронювання зберігають ціну, яка діяла під час оформлення.
Слайдер головної й room.html?room=slug також читають актуальні дані Supabase.
Старі чотири адреси rooms/*.html збережені й використовують ту саму базу.
Після зміни номера онови сайт або повернись до його вкладки. Генератор запускати не потрібно.
Завантаження нових фото до Supabase Storage тут ще не реалізовано: обираються наявні фото.

Перевірка після налаштування
1. Додай тестовий номер з унікальною адресою.
2. Онови адмінсторінку: запис має залишитися. Перевір його також у Table Editor → rooms.
3. Зміни ціну й перевір її на сторінці бронювання.
4. Вимкни доступність і переконайся, що номер зник зі списку бронювання після оновлення.
5. Видали тестовий номер без бронювань і перевір відсутність запису в rooms.
6. Увійди звичайним акаунтом: доступ до керування має бути закритий.

Захист
Роль задається записом hotel_admins.user_id → auth.users.id.
Браузер не має доступу до таблиці ролей. Звичайна реєстрація не дає прав адміністратора.
is_hotel_admin перевіряє користувача поточної сесії; RLS перевіряє кожну операцію rooms.
Призначати інших адміністраторів слід лише через SQL Editor під контролем власника.
Видалення рядка користувача з hotel_admins відкликає права на наступні запити.
Не запускай 001_initial.sql після налаштування адміністратора: він скидає права rooms
до початкового доступу лише на читання. За потреби відновлення повтори 003_admin_rooms.sql.
Довідка: https://supabase.com/docs/guides/database/postgres/row-level-security

Перевірки розробки
- tests/admin-api.test.cjs: node tests/admin-api.test.cjs (без додаткових залежностей).
- tests/admin-security.cjs: ізольована PostgreSQL/PGlite база з імітацією auth.uid();
  застосовує справжні SQL-файли 001–003, перевіряє заборону самопризначення,
  обмеження гостя/користувача, CRUD адміністратора, FK та відкликання ролі.
  Для запуску потрібен @electric-sql/pglite у середовищі Node; сайт його не використовує.
- У браузері виконано CRUD на ізольованих тестових даних, перевірено форму на ширині 375px
  і закритий доступ до справжньої сторінки без авторизації.
Міграцію та призначення ролі у твоєму Supabase потрібно виконати кроками вище.
